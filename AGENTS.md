# TheDobinator - Agent Policies & Guidelines

This document outlines the core policies, design patterns, and operational knowledge for any AI agents working on "theDobinator" project. 

## 1. Project Context & Tone
* **True Purpose:** The project automates the copying of files and setup processes for data drive builds.
* **Thematic Tone:** When writing user-facing documentation (like the README), maintain a serious, ironic tone suggesting that the robot is using AI to replace "Garrett 'Ace' Dobson."

## 2. Drive Monitoring & State Management
* **Ephemeral State:** The list of "known" or "ignored" drives must be stored in memory (e.g., a Python `set()`) so that the state resets completely every time the program restarts.
* **Startup Behavior:** The program must instantly fetch all connected drives upon startup and add them to the ignore list. It should only ever process drives that are connected *after* the script has begun running.
* **Re-insertion Processing:** If a drive is removed, it must be detected and removed from the internal ignore list. This ensures that if the same drive is re-inserted, it will be treated as a "new" connection and processed again.
* **Efficiency:** The main monitoring loop should poll frequently (e.g., every 2 seconds) using efficient OS-level calls (like `ctypes.windll.kernel32.GetLogicalDrives()` on Windows) rather than aggressive file-system scanning.

## 3. Drive Processing Logic (`dobd.py`)
* **Disk-level detection (`scan_external_disks`):** Detection is **physical-disk based**, not drive-letter based, because brand-new/uninitialized disks, RAW disks, and foreign filesystems (e.g. APFS) have **no drive letter** and are invisible to `GetLogicalDrives()`. A throttled PowerShell scan (`Get-Disk`/`Get-Partition`/`Get-Volume`, every `DISK_SCAN_EVERY` poll iterations) returns each non-system/non-boot disk's `{number, sizeTB, letter, fs, style, serial}`. The monitor loop keys the known/ignore set on **disk number**, establishes a startup baseline (only disks plugged in *after* start are processed — this also protects every pre-existing disk from being touched), and returns `None` on scan failure so a transient error never looks like "all disks removed".
* **Target Identification & Routing (`classify_and_enqueue_disk`):** A new disk with a readable, lettered volume (`NTFS/exFAT/FAT`) containing `packfiles.txt` → queued for the full build via `process_drive()`. **Everything else** — NTFS/exFAT/FAT with no packfiles, or RAW/uninitialized/foreign (APFS, brand-new) — → registered *blank-awaiting* (keyed by disk number) and surfaced as a WebUI popup; not processed until the user supplies a Drive Name + Country. (So exFAT/FAT *with* packfiles builds as-is; *without*, it gets reformatted NTFS.)
* **Drive job model & `DriveManager`:** Queue items are job dicts `{disk, path, kind: "packfiles"|"country", name, sizeTB, iso, serial}`. For packfiles jobs `path` is the existing drive letter; for country jobs `path` is `None` until `initialize_and_format_disk` assigns one. `DriveManager` (thread-safe, keyed by disk number) tracks two lists published to `status.json`: `BlankDrives` (`{token, sizeTB}`, each `token` unique so popups serialize) and `PendingDrives` (`{name, sizeTB}`).
* **Blank-drive submission IPC:** The WebUI popup POSTs `{token, name, country}` to the companion API's `/submit-drive`, which drops a JSON file into `logs/submissions/`. The monitor loop's `consume_submissions()` validates it, builds a `country` job (carrying the disk number + serial), and queues it. The user-entered name is sanitized (trim + internal whitespace → underscores) on **both** sides.
* **Disk formatting (`initialize_and_format_disk`) — DO NOT regress to `Format-Volume`-by-letter:** The old approach only worked on an already-mounted readable volume and left drives RAW/uninitialized. The correct, uniform approach clears the **whole disk**, (re)initializes GPT, creates a partition with an assigned letter, and quick-formats NTFS — handling every starting state (uninitialized, RAW, APFS, exFAT/FAT, NTFS) and returning the assigned letter. **Safety (mandatory):** the PowerShell script refuses `IsSystem`/`IsBoot` disks and verifies the disk's size (±1 TB) and serial number still match what was detected, so a reused disk number can never wipe the wrong disk. Only disks newly connected *after* startup ever reach this path.
* **Country-Drive Workflow (`process_country_drive`):** No LLM. (1) `initialize_and_format_disk` reinitializes+NTFS-formats the whole disk and captures the assigned letter (status 9; aborts with issues if it fails). (2) Region straight from the country: `USA` → US (`"u"`), anything else → International (`"i"`). (3) Copy regional base files (`copy_region_files`, status 3). (4) Non-US only: copy the three country-specific sets keyed on the ISO Alpha-3 code (`copy_country_files`, status 8 — imagery file(s) `<iso>_*` from `…\imagery\GLOBAL\COUNTRIES`, the **contents** of the `<iso>` vector folder from `…\vector\Baseline` copied directly into `…\data\vector` (NOT into a `\<iso>` subfolder), and the `<iso>` geocode folder from `…\geocode`). (5) Clean up `dobDir`; report completed.
* **WebUI Status Numbers:** Full build uses steps 1–7; the country-drive path adds step 9 ("Formatting Drive") and step 8 ("Copying Country Files", whose progress bar reuses the *main* file counters). Imagery verification (below) adds steps 12 ("Verifying Imagery"), 13 ("Correcting Missed Imagery", AI), and 14 ("Copying Corrected Imagery", progress bar reuses the *main* counters). `isProcessing` in `app.js` treats **every** status `>= 1` except the terminal 10/11 as processing (so 12–14 count); 0 is idle. `copy_region_files` accepts a `status_number` arg (defaults to step 3).
* **WebUI imagery-verification detail (steps 12–14):** Because the verify/correct stages can sit for a long time, the WebUI shows live detail under the spinner instead of a static screen. `StatusManager.set_verify_progress(run, max_runs, missing)` publishes four `status.json` fields — `VerifyRun` (current correction attempt 1..5, **0 = not yet in a correction pass**), `VerifyMaxRuns` (= `FIX_LOOP_MAX_RUNS`), `VerifyMissingCount`, and `VerifyMissing` (filenames). `fix_loop` calls it right before each `_run_fix_llm` (reading the judge's freshly-written `missedImagery.txt` via `_read_missed_imagery`); `verifySuccess` resets it to a clean baseline at the start of each drive, and `update(status_number=0)` clears it on idle. **The "show fewer than 3" rule is enforced on BOTH sides:** the backend only puts the actual basenames in `VerifyMissing` when `count < 3` (else it sends `[]` and just the count, so a long missing list never bloats the polled `status.json` or the screen), and `verifyDetail()` in `render.js` mirrors that — naming the files when present, otherwise showing only "Still searching for N imagery files." The detail block (`.verify-detail` / `.verify-attempt` / `.verify-missing*` in `styles.css`) is suppressed entirely on the initial pass (run 0, none flagged). **⚠️ Adding any new `status.json` field needs it added to `DEFAULT_STATE` (and `ERROR_STATE`) in `srvr/assets/js/api.js`** — `normalizeState()` *strips any key not present there*, so a field the bot writes will silently never reach `render.js` otherwise. The new fields are also added to render.js's `changed` gate so the card re-renders when they update.
* **Imagery verification (`verifySuccess`, packfiles drives only):** After mainCopy, `verifySuccess` returns `(issues_found, verified)`. The verification leg regenerates packfiles on the built drive and confirms the imagery set is complete: (1) `generate_packfiles` launches `DRIVE:\ARS\bin\ars maintenance.bat` (starts the ARS program), waits `ARS_SETTLE_SECONDS` (25s), force-quits ARS (`taskkill /IM ars.exe`), then MOVES the regenerated `…\ARS\bin\packfiles.txt` into `dobDir\verify_packfiles.txt` (replacing any prior copy). (2) **`_judge_missing_imagery`** (the gate, idea #3) compares the original `packfiles.txt` imagery list against `verify_packfiles.txt` and writes the *precise* still-missing list to `dobDir\missedImagery.txt`. It is **NOT a string diff** — copied files routinely carry a newer name (date/version/resolution drift) than the original entry. It runs in **two stages**: (a) a deterministic **product-key pass** (`_normalized_missing`/`_normalize_product_key`) clears renamed-but-present files (it reduces each name to a letters-only identity, so `usa-tx_naip_small_2023_61cm` ↔ `..._2024_61cm` and `usa_faa_..._2025-04-17` ↔ `..._2026-06-11` match) with **zero LLM risk**; (b) only the still-unmatched candidates go to the judge LLM (`JUDGE_LLM_MODEL` = `openai/qwen/qwen3.6-27b` @ 10k), which is now a **DIRECT chat completion (`LLM.chat_text`), NOT Open Interpreter** — we read the missing list straight off its text reply (`_extract_intended_misses`). **Why this matters (regression that bit twice):** under Open Interpreter the judge had to *write* `missedImagery.txt` via executed Python, and the small model frequently just replied in chat and wrote nothing; the OLD exact-string fallback then flagged **every renamed-but-present file** (e.g. all the FAA charts) as missing — making verification report ~14 false misses when only ~3 were genuinely absent. A verbatim-present fast path still short-circuits when nothing drifted; if the direct LLM call is truly unreachable, the deterministic candidates (no same-product entry on the drive) are used — **never** an exact-name diff. `compare_packfiles` verifies when the judge returns an empty list, else enters `fix_loop(1)`. (3) `fix_loop(n)` runs **at most `FIX_LOOP_MAX_RUNS` (5)** times: each run hands the corrective LLM the precise `missedImagery.txt` list, gets `dobDir\extraMapping{n}.csv`, and `_copy_from_mapping` robocopies it (`issues_filename=None`). Runs 2–5 first re-`generate_packfiles`+re-judge and stop early as verified if nothing is missing; run 5 does a final re-judge after its copy. **Early-exit (idea #2):** after any corrective run, if the LLM recorded genuinely-absent files in `dobDir\couldNotFind.txt`, the loop stops immediately and the drive is **unverified** (no later model can recover a file that isn't on U — don't burn the remaining runs). If ARS can't regenerate packfiles, verification is **skipped and assumed verified**. Country/no-packfiles drives are always `verified=True`. `mainCopy` and `fix_loop` share `_copy_from_mapping`.
* **Why count-only verification was abandoned:** the original `compare_packfiles` just counted `data\imagery\` lines. A real drive then "passed" because the corrective LLM, unable to find a genuinely-absent file (`usa_faa_ifr_enr_gom_vertical_flight_ref`, 0 matches on U), fuzzy-substituted a WRONG file (Texas→Tennessee) and the substitute bumped the count to target → falsely `verified=1`. The fix is twofold: the judge compares by *product identity* not count, and the corrective prompt forbids substitution + reports genuine absence.
* **Model variation across stages (deliberate):** matchFiles (initial build) uses `openai/qwen/qwen3.6-27b`; the imagery judge uses `openai/qwen/qwen3.6-27b` @ 10k (`JUDGE_LLM_MODEL`); correction runs 1–4 use `openai/qwen/qwen3.6-35b-a3b` @ 40k (`FIX_LLM_MODEL`); the final correction run (5) uses `openai/google/gemma-4-31b` @ 10k (`FINAL_FIX_LLM_MODEL`). Varying the model per stage is intentional. **Do not "unify" these models.** All exist on the LM server (verify with `GET /v1/models`); the `openai/` prefix is the litellm provider tag, the server-side id is the part after it (e.g. `qwen/qwen3.6-35b-a3b`).
* **Corrective-LLM correctness rules (in the `_run_fix_llm` prompt):** The fix prompt forbids the failure modes seen in testing — it must (1) output ONLY `dobDir\extraMapping{n}.csv` as a real 2-column CSV (no scratch/notes, and any temp file must stay in dobDir, never the drive root), (2) NEVER rename a file (destination basename must equal the U-drive source basename), (3) NEVER substitute a different file to fill a gap (no fuzzy cross-state/region matches — e.g. Texas→Tennessee), and (4) for a file genuinely absent from U, leave it out of the CSV AND record it in `dobDir\couldNotFind.txt` (only when confident — "unsure" means leave it out of both so another run can try). It is fed the judge's *precise* missing list, not two raw lists to diff. It is also told **how** to work — locate files with small, targeted commands and write the tiny CSV in one short final step — explicitly *not* to write a big general-purpose search script (that over-engineering is what hit the output-token cap and produced nothing; see §"output-truncation"). **Only the verify/correct prompts' strategy may be tuned; the matchFiles prompt's strategy is left alone** — the *one* exception is the destination DRIVE LETTER, which is now templated for both (see "drive-letter templating" below).
* **⚠️ Drive-letter templating (`build_match_files_prompt(drive_path)` / `_drive_letter`) — the prompt is no longer a bare constant:** `MATCH_FILES_PROMPT` used to be a module constant whose examples hardcoded `D:` as the destination (`D:ARS\data\...`). Weaker models copied that literally and wrote mapping rows targeting `D:` even when the drive being built was `F:`, so the copies went nowhere. It is now a *builder* that injects the real target letter from `drive_path` (e.g. `F:\ARS\data\...`) and states "this drive is the F: drive" up front. `_run_fix_llm` uses the same builder. If you edit the prompt, keep it a function of `drive_path`; never reintroduce a hardcoded drive letter.
* **⚠️ Cross-drive contamination guard (`_is_trusted_source` / `MASTER_SOURCE_ROOT`) — DO NOT remove:** The only legitimate source of build files is the read-only U: master at `U:\ARS\Data` (every base/country robocopy and the matchFiles/fix prompts all use it). But matchFiles & fix_loop run under Open Interpreter with **unrestricted filesystem access**, so when a *second packfiles drive is plugged in at the same time* as the one being built, the agent can see that other drive's `ARS\data` tree and map a file off of **it** into `mapping.csv`; `_copy_from_mapping` (shared by `mainCopy` and `fix_loop`) then robocopies that foreign file onto the wrong drive. This actually happened: an NM build picked up three Tulare-county files (`terrain_usa-ca-tularecounty-…`, `terrain_usa-nc_…`, `usa-ca-fresno_…`) that were never in NM's `packfiles.txt`. The imagery judge never caught them because verification only checks that every **intended** file is PRESENT — it never checks for **extra** files. The fix is a deterministic backstop in `_copy_from_mapping`: every mapping row's **source** must resolve under `MASTER_SOURCE_ROOT` (case-/slash-insensitive) or the row is skipped and logged as an error (surfaces in ISSUES for `mainCopy`). It is a no-op on correct builds (all real sources are under U:) and does **not** touch the agent prompts or processing flow.
* **Drive-root scatter cleanup (`_snapshot_root_entries`/`_clean_root_scatter`):** matchFiles & fix_loop run with the drive root as CWD, so Open-Interpreter scratch files (e.g. `iv_matched.txt`, `missing_files.txt`) land at the root and survive the dobDir cleanup. `process_drive` snapshots the root right after creating dobDir and, at the end, deletes only top-level **files** that appeared during processing — never directories (ARS/dobDir/System Volume Information), never pre-existing files (original packfiles.txt), and never `ISSUES.md`.
* **`completedDrives.csv` schema & history coloring:** Rows are `timestamp,name,issues(0/1),verified(0/1),missingImagery("|"-joined filenames)`. `verified` (4th col) and `missingImagery` (5th col) are newer — legacy 3-/4-column rows default to `verified=True` / `[]`. Only the **filename** (basename) of each missing entry is stored. The WebUI's Completed Drives list colors **green** when verified (and no issues), **yellow** when not verified (with a "Not all imagery files were found." note) or when copy issues occurred; for unverified drives with a non-empty `missingImagery` it adds a collapsible `<details>` "N file(s) unavailable on the source drive" disclosure listing them. The list is keyed/sorted by timestamp (never by name) so duplicate drive names render and clear correctly. The topbar history modal's **Clear** button is a per-browser view action: it stores the newest cleared timestamp in `localStorage` (`dob_completed_cleared_before`) and hides anything at/before it — the CSV and `status.json` are untouched, so drives "stay in the csv".
* **`status.json` concurrency:** It is now written from multiple threads (worker + monitor loop), so `StatusManager` guards every read-modify-write with an `RLock`.
* **Ephemeral drive lists / stale-popup safety:** `BlankDrives`/`PendingDrives` are transient and must never survive a restart. (1) `dobd.py` calls `DriveManager.reset()` at startup and clears the lists in its `finally`. (2) Because `quit.bat` **force-kills** `dobd.py` (so its `finally` may not run) and a hard reboot freezes `status.json`, `srvr_api.py` also scrubs the transient fields (`Running`/`StatusNumber`/`BlankDrives`/`PendingDrives`/counters) at its own startup **iff** no `dobd.py` process is running — this is what prevents a phantom naming-popup after a reboot. (3) The WebUI treats `Running != 1` as "no blank/pending drives" (suppresses the popup, the name-drives button, the pending badge, and the pending list), so powering off/quitting visibly clears everything even if the on-disk JSON still holds stale entries.
* **⚠️ WebUI design language — every addition MUST fit the existing look:** The portal has a deliberate, minimal aesthetic (JetBrains Mono throughout, the `--bg/--fg/--muted/--success/--warning/--danger` + `--radius-*` + `--ease` tokens in `styles.css`, soft cards, subtle borders, restrained motion). **Any** new UI — buttons, modals, lists, notes, badges — must reuse those CSS variables and existing component classes (don't hardcode colors/radii, don't introduce a new font or a jarring style), match the surrounding spacing/typography, and feel like it was always there. It must also **work well on BOTH mobile and desktop**: test at the `mobile` (≈375px) and `desktop` presets, ensure text wraps (`word-break` for long filenames/paths), long lists scroll (cap with `max-height`) rather than blowing out the layout, and tap targets stay usable. Prefer native, accessible primitives (e.g. `<details>` for disclosures) over custom JS widgets. When you add or change anything visible, load the preview and verify it actually looks good at both sizes before finishing.
* **Unplugged-drive handling:** On disk removal the monitor loop drops it from both the blank-awaiting and pending lists (by disk number). A packfiles job already in the queue is additionally skipped by the worker via an `os.path.exists` guard on its letter; a country job (no letter yet) is guarded by `initialize_and_format_disk`'s size+serial re-verification, which aborts rather than format a disk that's gone or been swapped.
* **Blank-drive popup UX:** The naming popup has a close (X) that hides it without losing the drive (`promptHiddenByUser`); a pulsing topbar "name drives" button (visible only while running with blank drives awaiting) reopens it. This is what lets the operator reach the power button to quit while drives are awaiting names.
* **Initial Actions:** When a target drive is identified, the first action is to create a `dobDir` directory on the root of the drive.
* **Modularity:** Any new processing functions should be called from within the explicitly marked comment section in the `process_drive()` function to keep the script organized.
* **Temporary Files:** If the python file ever needs to make any temporary files, it must put them in the `dobDir` directory on the target drive.

## 4. Logging & Verbose Tracking Policy
* **Log Location:** All logs must be written to `logs/dobLog.log` at the root of the project.
* **Auto-Resetting:** The log file must reset on every run. Use the file handler mode `'w'` (overwrite) instead of `'a'` (append).
* **Verbosity Requirement:** Logging must be *extremely* verbose to ensure any problems can be easily diagnosed. Use the standard Python `logging` module and output to both the file and the console.
* **Severity Levels:**
    * `DEBUG`: Use for highly verbose tracing, variable tracking, polling loop updates, path checking, and internal state modifications.
    * `INFO`: Use for standard operational steps, program startup/shutdown, and confirming processing checkpoints.
    * `WARNING`: Use strictly for alerting when physical drive changes occur (a new drive is detected or a drive is removed).
    * `ERROR/CRITICAL`: Use for exceptions, failed folder creations, and stack traces.
* **Adding new logs is encouraged (operator-blessed):** You are explicitly free to add a new dedicated log whenever it would help diagnose or observe the bot — you do not need to ask first. Do **not** go out of your way to invent logs no one needs, but never withhold one that would genuinely aid debugging. Any new log must follow the per-program/per-thread separation rules below (own file in `logs/`, matching `*Prev.log` rotation via `rotate_prev_log`, dedicated `getLogger(...)` with `propagate=False`, shared console `stream_handler`, `LessNoiseFilter`). `*.log` is already gitignored, so new logs never get committed.
* **Per-Thread / Per-Program Log Separation (going forward):** Every new Python thread, and every new standalone Python file/program added to the project, must write to its **own dedicated log file** in `logs/` (e.g. `logs/<name>.log`) with a matching `logs/<name>Prev.log` that keeps the last 5 runs — the same rule applied to `dobLogPrev.log`. Do **not** funnel a new thread's output into `dobLog.log`; keep each concern in its own file so the main log stays readable.
    * **Precedent:** The polling process (the drive-scanning loop in `main()` plus the GitHub `UpdateWatcher`) logs to `logs/pollingLog.log` / `logs/pollingLogPrev.log` via a dedicated `logging.getLogger("dobinator.polling")` (referenced as `plog`) configured with `propagate = False` so its records never reach `dobLog.log`. The rest of the bot keeps using the root logger → `dobLog.log`.
    * **Context-usage log (`logs/contextLog.log`, logger `clog` = `dobinator.context`):** One line per finished LLM run recording **what percent of the model's context window the run consumed**, the model name, and the window size. Plumbing: `llm_runner.py` computes the usage after `interpreter.chat()` (via `litellm.token_counter` over the full final message list, falling back to a char/4 estimate) and prints a single `__DOB_CONTEXT_SENTINEL__`-style line (`CONTEXT_SENTINEL`); the `LLM` class in `dobd.py` parses that line out of the child's stdout (it is NOT written to `llmRunner.log`) and `clog`s it. Timeouts/crashes log a `context=UNKNOWN` line so every run leaves a record. **Direct (non-OI) calls** (`LLM.chat_text`, e.g. the imagery judge) also log here, tagged `dir=(direct)`, using the server's own `usage` token counts. Same `*Prev.log` rotation as the others.
    * **Rotation:** Use the shared `rotate_prev_log(log_file, prev_log_file)` helper for the `*Prev.log` roll-over so every log behaves identically. Apply the same `LessNoiseFilter` to new handlers, and add the shared console `stream_handler` to the new logger so nothing disappears from the live console.

## 5. Hosting & Deployment (IIS / dobinator.c-nav.com)
* **Where it runs:** theDobinator runs on a Windows 11 PC in the office. The WebUI is hosted **locally on that same PC via IIS** and reachable at **`dobinator.c-nav.com`**. IIS serves the static front-end out of `srvr/` (`index.html` + `assets/css/styles.css` + `assets/js/app.js` + `status.json`); the companion API (`srvr_api.py`) runs as the "Dobinator Web API" scheduled task and is the dynamic backend.
* **⚠️ That same PC now hosts a SECOND site — `drivelabel.c-nav.com` (see §5b).** IIS distinguishes them by **host header**, both on port 80. theDobinator's binding must stay **blank-hostname (catch-all)** so `http://<box-ip>/` keeps working; the Drive Label site owns the explicit `drivelabel.c-nav.com` binding. Ports in use on the box: **80** (IIS, both sites), **5050** (Dobinator API), **5051** (Drive Label API).
* **⚠️ Browser/proxy caching — caching is disabled on purpose, keep it that way:** Because IIS serves the WebUI as plain static files, browsers were caching `index.html`/`styles.css`/`app.js` and operators kept seeing a **stale UI after a WebUI change** until they hard-refreshed. The fix lives in **`srvr/web.config`** and **must not be regressed**:
    * `<staticContent><clientCache cacheControlMode="DisableCache" /></staticContent>` — the IIS-native switch that stops it from emitting far-future `Expires`/`Cache-Control: max-age` on static files.
    * A **site-wide** `<system.webServer><httpProtocol><customHeaders>` block adds `Cache-Control: no-cache, no-store, must-revalidate`, `Pragma: no-cache`, and `Expires: 0` to **every** response as a backstop.
    * These apply globally, so do **not** re-add the same `customHeaders` inside a `<location>` (e.g. the old per-file `status.json` block, now removed) — duplicating a header name in a child scope makes IIS throw **HTTP 500.19 (duplicate collection entry)** and the whole site 500s.
* **Deploying a WebUI change:** Editing the files in `srvr/` updates what IIS serves immediately (no build step). With caching disabled, a normal browser reload now picks up changes — no hard-refresh needed. `web.config` edits are re-read by IIS on the next request (no reboot), but changes to `srvr_api.py` still follow the reboot-required rule in §6 below.

## 5b. Print Label — MOVED OUT to its own site (`drivelabel.c-nav.com`)
* **⚠️ Label printing is NOT part of theDobinator's portal any more. Do not re-add it.** It was a modal (`#printModal`) inside `srvr/index.html` with its logic in `app.js` and two endpoints in `srvr_api.py`. All of that is **gone**: the modal, `openPrintModal`/`collectPrintConfig`/`handlePrintLabel`/`fillPrintForm`/`setPrintStatus`/`PRINT_FALLBACK_DEFAULTS`/`setVal`/`getVal` in `app.js`, `fetchPrintDefaults`/`printLabel` in `api.js`, `.form-section`/`.print-status` in `styles.css`, and the whole driveLabelPrinter block plus the `/print-defaults` and `/print-label` routes in `srvr_api.py`.
* **What's left in theDobinator:** `#printBtn` in the topbar is now a plain **`<a href="http://drivelabel.c-nav.com/" target="_blank">`** — the printer icon just opens the other site. It keeps the shared `.print-btn` topbar styling (which gained `text-decoration: none` for the anchor). There is deliberately **no** click handler for it in `app.js`.
* **Where it lives now:** the `drivelabel/` folder in this repo — a **React (Vite) site** plus its own companion API. See **`drivelabel/README.md`** for the full picture; the essentials are below.
* **Two sites, one PC, one port:** IIS hosts both on **port 80**, told apart by **host header**. theDobinator's site keeps its blank-hostname (catch-all) binding so `http://<box-ip>/` still reaches it; the new "Drive Label" site binds `http/*:80:drivelabel.c-nav.com`. **Do not add a host header to theDobinator's binding** — that would break access by IP. `drivelabel/setup_drivelabel.bat` (self-elevating, idempotent) creates the site, grants `IIS_IUSRS` read, opens TCP 5051, and registers the scheduled task.
* **⚠️ `drivelabel/site/` is BUILT OUTPUT and is COMMITTED — this is load-bearing.** The office PC has no Node and no build step; the git updater only does `git reset --hard origin/main`, so the finished files must already be in the repo. The React **source** is `drivelabel/app/`; `npm run build` writes `drivelabel/site/` (via `outDir: '../site'`). **Any change to `app/` must be rebuilt and committed together with the regenerated `site/` output in the same commit**, or the host keeps serving the old UI. Never hand-edit `site/` — the next build wipes it. `web.config` lives in `app/public/` precisely so the build copies it into `site/`; it carries the same deliberate no-cache settings as §5.
* **Its own API — `drivelabel/label_api.py` on port 5051:** `GET /health`, `GET /print-defaults`, `POST /print-label`. ## 6. Living Document Policy
* **Knowledge Preservation:** If you discover a "gotcha", a repeated requirement, or a useful piece of project context that would benefit future agents, you must document it here immediately to ensure continuous knowledge preservation.
* **⚠️ Reboot-required updates — SET THIS FLAG:** The file `configs/reboot_required.flag` (committed; contains `1` or `0`) tells the WebUI whether the *currently published* update needs a full PC restart to take effect. **Any time you make a change that requires the PC to be rebooted to take effect — e.g. anything that changes `srvr/srvr_api.py`, a scheduled task, a service, or other long-lived process that only re-reads its code on reboot — you MUST set `configs/reboot_required.flag` to `1` in that same commit. For an ordinary change that does NOT need a reboot, set it back to `0`.** The bot's `UpdateWatcher` reads this file's content *from the remote* when it detects a new commit and publishes `RebootRequired` into `status.json`; the WebUI then turns the update button **red** ("Restart required" on hover) instead of yellow. Clicking the red button updates from git, clears the local flag, and reboots the PC (`git_update.py --reboot`).
* **Elevation requirement (disk formatting):** Country/blank-drive builds run `Clear-Disk`/`Initialize-Disk`/`Format-Volume`, which require **administrator** rights. The bot is spawned by the companion API (`srvr_api.py` → `dobWin.bat` → `dobr.vbs` → `dobd.py`) and inherits its token, so the **"Dobinator Web API" scheduled task must be set to "Run with highest privileges"** (and the logged-on user must be a local admin). `dobd.py` logs its elevation state at startup (`is_admin()`); if it logs "NOT elevated", formatting will fail and the task needs the highest-privileges box checked. `shutdown /r` for reboot-updates also relies on this elevation.
* **⚠️ UTF-8 stdout is mandatory for `llm_runner.py` (cp1252 crash) — DO NOT remove `_force_utf8_stdio()`:** Open Interpreter streams the model's reply straight to `stdout`. On Windows a subprocess's piped stdout defaults to the legacy ANSI code page (cp1252), so the instant a model emitted an ordinary character outside Latin-1 — e.g. `→` (U+2192) or `•` (U+2022), which agents print *constantly* when narrating "source → destination" mappings — `print()` raised `UnicodeEncodeError` and the whole chat aborted (exit 5), silently discarding the matchFiles/judge/fix work **mid-run**. This was a leading cause of "files randomly missing on some builds but not others." `llm_runner.py` now calls `_force_utf8_stdio()` (reconfigures `stdout`/`stderr` to UTF-8 `errors="replace"`) before anything prints, and `dobd.py` also sets `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8` on the child env. Keep both.
* **Corrective/match LLM output-truncation gotcha (`max_tokens`) — FIXED, keep the headroom:** The fix-loop corrective LLM is asked for a tiny 2-column CSV but used to *over-engineer a long Python script* to build it; with the old `max_tokens=4096` the generated code block got cut off mid-line → Jupyter `SyntaxError: incomplete input` → the code never ran → no `extraMapping{n}.csv` → nothing recovered (observed failing all 5 runs). Two-part fix: (1) the output-token caps were raised and split per stage — `DEFAULT_MAX_TOKENS=8192`, `MATCH_MAX_TOKENS=16384` (matchFiles writes the whole mapping.csv via code), `JUDGE_MAX_TOKENS=2048` (short list, 10k ctx), `FIX_MAX_TOKENS=12288` (runs 1–4), `FINAL_FIX_MAX_TOKENS=4096` (gemma, 10k ctx) — each kept below its stage's context window; (2) the corrective prompt now tells the model to use small targeted look-ups and write the CSV directly rather than scripting a search. If imagery keeps coming back unrecovered, check `contextLog.log` for output/context pressure before suspecting "the file isn't on U". **Do not drop these caps back to 4096.**
* **LLM run reliability — model preflight, retry, and per-stage timeouts (`_preflight`/`max_attempts`/`*_RUN_TIMEOUT_S`):** The models run on a **local OpenAI-compatible server (LM Studio, `192.168.11.65:1234`, 2×RTX 3090)**. The pipeline deliberately rotates through several models (matchFiles/verify = `qwen3.6-27b`; judge = `qwen3.6-27b`@10k; fix 1–4 = `qwen3.6-35b-a3b`@40k; fix 5 = `gemma-4-31b`@10k), and the box can't keep them all resident — so each **model switch triggers an unload/load**, and the first request during that window can stall or return a server error. Open Interpreter hitting that mid-chat used to **hang until the 45-min watchdog**, burning the whole budget (seen as an `AuthenticationError` traceback followed by a 2700s timeout). Mitigations, all in the `LLM` class: (1) **`_preflight()`** sends a cheap 1-token completion (retried with backoff) before each real run so it only starts once the model has loaded; (2) **`useLoc` retries** a failed run (timeout/non-zero exit) in a fresh subprocess up to `max_attempts` (=`LLM_RUN_ATTEMPTS`, 2); (3) **per-stage timeouts** — matchFiles keeps the generous `LLM_RUN_TIMEOUT_S` (2700s, legit runs take ~27 min), but the quick stages get `JUDGE_RUN_TIMEOUT_S` (900s) / `FIX_RUN_TIMEOUT_S` (1500s) so a hung judge/fix is killed and retried in minutes, not 45 min. Keep these; do **not** unify the models (the variation is intentional — see model-variation note above).
* **Open Interpreter Dependency Gotcha:** When calling `OpenInterpreter` from within a Python script (especially if `open-interpreter` was installed via `pipx`), Open Interpreter will attempt to use the script's `sys.executable` to spawn Jupyter kernels. If the system Python environment running the script does not have `ipykernel` installed, Open Interpreter will **hang silently forever** when asked to execute Python code. Always ensure `python -m pip install ipykernel` has been run on the host Python.

## 7. Background Git Updater Architecture & History
* **⚠️ "Update pending" must be derived from local-vs-remote SHA, not from "pushes seen since startup":** `UpdateWatcher` in `dobd.py` lights up the WebUI update indicator. It uses cheap ETag conditional requests for in-session detection, **but the source of truth for whether an update is pending is `get_local_head_sha()` (the working tree's checked-out commit) compared against the remote `main` HEAD SHA** (parsed from `/commits?per_page=1`). This comparison happens on the watcher's first (baseline) check, so a pending update **survives a power cycle** — previously the watcher only baselined its ETag and assumed "the version I started on is current", which silently dropped a still-pending update whenever the operator powered off and on without applying it. `get_local_head_sha()` reads `.git/HEAD` → loose ref → `packed-refs` directly (never shells out to git, whose PATH is unreliable under a logon-spawned process). Don't regress this back to ETag-only detection.
* **Goal:** Automate pulling the latest `main` from `https://github.com/TheTrueProblematic/theDobinator.git` daily at 5:00 AM. The updater must (1) skip the run if the program is mid-task, (2) cleanly shut down the program via `src/quit.bat`, (3) bring the working tree to match `origin/main`, and (4) relaunch via `dobWin.bat`.
* **Components:**
    * `configs/git_setup.bat` — Run once by `configs/win_setup.bat`. Installs Git via `winget` if missing, refreshes PATH, registers `PROJECT_ROOT` as a `safe.directory` globally, kills stale watchers, creates the `Dobinator Git Updater` scheduled task (on-logon), and starts `dobGit.vbs` immediately.
    * `configs/dobGit.vbs` — Long-running watcher. Resolves `pythonw.exe` from a list of standard install locations (PATH is unreliable when launched from `wscript` at logon), then loops forever: sleep until the next 5:00 AM, run `git_update.py`, log the exit code, repeat. Errors inside the loop are swallowed (`On Error Resume Next`) so a single bad day does not kill the watcher.
    * `configs/git_updater/git_update.py` — The actual update logic. Accepts `--reboot`: after pulling, it clears `configs/reboot_required.flag` and runs `shutdown /r` instead of relaunching the bot. The WebUI's red "Restart required" button hits the API's `/update-reboot` (idle) or `/schedule-update-reboot` (mid-drive → the bot calls `trigger_update(reboot=True)` after the drive); both end up running `git_update.py --reboot`.
    * `configs/dobGitManual.bat` — Manual trigger; runs `git_update.py` directly and pauses so the operator can inspect results.
* **Why the Git approach kept "silently succeeding" but not updating:** Two compounding bugs in the prior implementation.
    1. `subprocess.run("git init", shell=True, ...)` had **no return-code check**. Only the final `git reset --hard` was checked. If `git.exe` was unresolvable from PATH (very common when launched by `wscript`->`pythonw` on logon — winget puts Git on user-PATH which a logon-task environment may not inherit), every preceding step failed silently and the final reset failed with a generic non-zero, mis-attributed to "no changes".
    2. `git remote add origin` fails on a second run because the remote already exists, but again, the failure was unchecked. Newer Git versions also refuse to operate on directories with "dubious ownership" (exit 128) — easy to hit when the project was unzipped/copied by a different user than the one running the scheduled task.
* **Current (working) design — must be preserved:**
    * `find_git_executable()` locates `git.exe` via `shutil.which` and a fallback list of typical Git-for-Windows install locations. Never trust PATH.
    * `run_git()` is the only way to call git: list-arg form (NEVER `shell=True`), `stdin=DEVNULL`, both stdout and stderr captured and **fully logged**, return-code checked by default, with `GIT_TERMINAL_PROMPT=0` set so any credential prompt fails fast instead of hanging the daemon.
    * `_ensure_safe_directory()` adds `PROJECT_ROOT` to global `safe.directory` on every run (idempotent).
    * `_is_valid_repo()` uses `git rev-parse --is-inside-work-tree` — relying on the presence of a `.git` folder is not sufficient (a partial/corrupt `.git` from an earlier failed init looks "present").
    * If not a valid repo, `_initialize_repo()` wipes any stale `.git`, runs `git init --initial-branch main`, sets local identity, and adds origin.
    * If it is a valid repo, `_ensure_remote_url()` rewrites origin's URL when it disagrees with `REPO_URL`.
    * After `git fetch --prune origin main`, the tree is brought up to date with `git reset --hard origin/main`. If that fails because of conflicting untracked files (paths present locally as untracked but tracked in origin), `_resolve_untracked_conflicts()` deletes only those specific files and the reset is retried once. Files matched by `.gitignore` (logs, `srvr/status.json`, `.DS_Store`) are always left alone — that's a property of `reset --hard`.
* **Do NOT regress to:** `shell=True`, `git pull` without explicit fetch+reset, skipping return-code checks on the early git commands, or the ZIP-download approach (it cannot delete files that were removed upstream, so the working tree drifts).
